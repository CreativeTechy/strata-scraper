# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Architecture

Pipeline: Scrapy spider → validate/dedup → Postgres → FastAPI → React dashboard.

**This app collects only.** There is no AI analysis stage: an article is stored with no analysis on it and `analysis_status='pending'`, and leaves through the JSONL export for whatever analyzes it (strata-media, this repo's upstream, is the intended consumer - see "Handoff" below). The LLM that remains is used to decide *what to collect*, never to interpret what was collected.

- `backend/scraper/spiders/source_rss.py` - Scrapy spider; reads sources from the `sources` table (scoped to the selected project's sources when `PIPELINE_PROJECT_ID` is set), discovers article links, extracts text via trafilatura. `keyword` sources are crawled via their Google News RSS feed (`googlenewsdecoder` resolves each item's `news.google.com/rss/articles/...` redirect-wrapper link to the real publisher URL before fetching it), GDELT's free news-search API (`backend/scraper/gdelt.py`, on by default - toggle with `GDELT_ENABLED`) fetched directly as articles, and - when `GOOGLE_CSE_API_KEY`/`GOOGLE_CSE_ENGINE_ID` are set - a general web search via `backend/scraper/web_search.py`, crawled like a `web` source; none of these three surface X/Twitter content (X blocks generic web crawlers and most of its own indexing), so a fourth tier, `backend/scraper/apify_twitter.py`, asks Apify's hosted tweet-search actor for tweets matching the keyword directly when `APIFY_API_TOKEN` is set (see below). `hashtag` sources (`x.com/hashtag/<tag>`) can't be crawled directly - unlike a `username` profile page, which X still server-renders a few `/status/` links into, a hashtag/search page is a pure client-rendered shell with no tweets or links anywhere in its raw HTML (confirmed against the live site, including with a spoofed Googlebot user-agent - X's `robots.txt` allows Googlebot there, but the response it actually serves is still just meta tags). Two independent best-effort tiers make up for that instead: when `GOOGLE_CSE_API_KEY`/`GOOGLE_CSE_ENGINE_ID` are set, `start()` asks Google CSE for individual tweet URLs mentioning the hashtag (often sparse, since X blocks most of its own site from being indexed) and only follows the results that are actual `/status/` links, feeding them through the same fxtwitter hydration path (`_yield_article`/`_hydrate_tweet`) used for tweets discovered via a profile page; when `APIFY_API_TOKEN` is set, `start()` also queries the same Apify tweet-search actor used for `keyword` sources, directly for the hashtag - its dataset already carries full tweet text, so those results are yielded as articles straight away rather than URLs to hydrate. Without either configured, a hashtag source reports 0 articles with an explanatory fetch note (see `source_diagnostics.py`) rather than a silent miss.
- `backend/scraper/apify_linkedin.py` - LinkedIn scraping tier for `linkedin` sources, called from `source_rss.py`'s `start()` in place of the normal seed HTTP request (not alongside it, unlike the `keyword`/`hashtag` tiers above) - LinkedIn requires an authenticated, JS-rendered session for every page, even a public company page, so there is no unauthenticated HTML worth fetching the way there is for X/Reddit/Telegram. Gated on `APIFY_API_TOKEN`; unconfigured, a `linkedin` source reports 0 articles with an explanatory fetch note, same contract as the CSE/GDELT/hashtag tiers. A `linkedin` source's stored URL itself carries its kind (`linkedin_kind(url)` reads it back off the path, no separate column - same pattern as `reddit`'s URL-shape-encodes-kind approach in `sources_store._derive_reddit_url`): `linkedin.com/company/<slug>` or `/in/<slug>` (that account's recent posts, via `APIFY_LINKEDIN_POSTS_ACTOR`) or `/search/results/content/?keywords=...` (posts matching a query across LinkedIn, via `APIFY_LINKEDIN_SEARCH_ACTOR`) - see `sources_store._derive_linkedin_url` for how a bare company/profile slug or search phrase (plus the dashboard's `linkedin_kind` selector, mirroring `reddit_kind`) resolves to one of these. Both default actors (harvestapi's) return dataset items in the same post shape (`linkedinUrl`/`content`/`author`/`postedAt`), confirmed live, so one normalizer covers company, profile, and search results alike.
- `backend/scraper/apify_threads.py` - Threads scraping tier for `threads` sources, same replaces-the-seed-request treatment as `linkedin` above (not alongside it) - threads.com is a JS-rendered SPA that gates most of a profile's posts behind a logged-in session, the same "no unauthenticated HTML worth fetching" situation LinkedIn is in. Gated on `APIFY_API_TOKEN`/`APIFY_THREADS_ACTOR` (default `automation-lab/threads-scraper`); unconfigured, a `threads` source reports 0 articles with an explanatory fetch note, same contract as an unconfigured `linkedin` source. A `threads` source's stored URL carries its kind the same URL-shape-encodes-kind way as `linkedin`/`reddit` (`threads_kind(url)`, no separate column): `threads.com/@<handle>` (that account's recent posts, via the actor's `posts` mode) or `threads.com/search?q=...` (posts matching a query, via the actor's `search` mode) - see `sources_store._derive_threads_url` for how a bare handle or search phrase (plus the dashboard's `threads_kind` selector) resolves to one of these; `threads.net` (Meta's former domain, still live as a redirect) is accepted as input and canonicalized to `threads.com`. Unlike the other Apify tiers, the actor's dataset field names are taken from its published docs rather than confirmed against a live run (no Apify token was available while building this), so `_article_from_post` checks a couple of likely aliases per field defensively.
- `backend/scraper/apify_facebook.py` - Facebook scraping tier for `facebook` sources, same replaces-the-seed-request treatment as `linkedin`/`threads` above (not alongside it) - a Facebook page, group, profile, or search-results page is either gated behind a login wall or served as a client-rendered shell, the same "no unauthenticated HTML worth fetching" situation LinkedIn/Threads are in. Gated on `APIFY_API_TOKEN`; unconfigured, a `facebook` source reports 0 articles with an explanatory fetch note, same contract as an unconfigured `linkedin`/`threads` source. Unlike LinkedIn's clean `/company/` vs `/in/` split, a plain `facebook.com/<slug>` vanity URL is genuinely ambiguous between a page and a personal profile - Facebook uses the identical shape for both - so a `facebook` source's stored URL carries its kind (`facebook_kind(url)`, no separate column) with one extra wrinkle on top of the usual URL-shape-encodes-kind pattern: `facebook.com/groups/<slug>` or a `facebook.com/share/g/<code>` group-share redirect link (confirmed live: a plain 302 straight to the canonical group URL, which `APIFY_FACEBOOK_GROUPS_ACTOR` follows itself) (group, via `APIFY_FACEBOOK_GROUPS_ACTOR`), `facebook.com/people/<name>/<id>` or `facebook.com/profile.php?id=<id>` (profile, unambiguous shape, via `APIFY_FACEBOOK_PROFILE_ACTOR`), `facebook.com/search/top/?q=...` (search, via `APIFY_FACEBOOK_SEARCH_ACTOR`), and a bare `facebook.com/<slug>` (page, via `APIFY_FACEBOOK_PAGES_ACTOR`, the default for this shape) unless it carries the `fb_kind=profile` marker `sources_store._derive_facebook_url` appends when the user explicitly picked "profile" for a bare slug - `_actor_target_url` strips that marker again before any URL is handed to an actor. Each of the four actors gets its own env var (`APIFY_FACEBOOK_PAGES_ACTOR`/`_GROUPS_ACTOR`/`_SEARCH_ACTOR`/`_PROFILE_ACTOR`) since page/group/profile/search have no shared dataset shape the way LinkedIn's two actors do. Unlike `apify_threads.py`, every actor/field choice here was confirmed against real dataset items from a live run, not just guessed by name - two nearby-sounding actors turned out to be the wrong tool and were replaced: `apify/facebook-pages-scraper` (a plausible first guess for "page") only returns page metadata (likes, address, phone, rating), never post text, so `APIFY_FACEBOOK_PAGES_ACTOR` defaults to `apify/facebook-posts-scraper` instead, which actually returns post captions with the same `startUrls`/`resultsLimit` input `apify_facebook_group_posts` also uses; `apify/facebook-profile-scraper` doesn't exist on Apify at all (confirmed 404), so `APIFY_FACEBOOK_PROFILE_ACTOR` defaults to `cleansyntax/facebook-profile-posts-scraper` instead (picked over ~10 other third-party candidates for its 99%+ live success rate), which takes a different input shape entirely (`endpoint`/`urls_text`/`max_posts`, keyed by an endpoint selector) and a different dataset shape (`message`/`author.name`/a raw Unix-epoch `timestamp` with no ISO field, vs. the other two actors' `text`/`user.name`/ISO `time`) - `_article_from_post`'s several field aliases and `_published_value`'s epoch-to-ISO conversion exist specifically to cover this actor. `apify/facebook-search-scraper` (the original "search" pick) turned out to be a Page directory finder (its real input field is `categories`, a Page name/category, not post content) whose dataset items are Page listings (`pageName`/`address`/`phone`/`rating`/`followers`) with no post-text field at all - confirmed live, it could never have produced an article - so `APIFY_FACEBOOK_SEARCH_ACTOR` now defaults to `cleansyntax/facebook-profile-posts-scraper` as well, using that same actor's `search_posts_by_keyword` endpoint, which genuinely searches post content (confirmed live against the exact query that used to return nothing) and shares the profile endpoint's dataset shape but not its slowness (~7-9s per query vs. ~55s+ for one profile's posts, hence `APIFY_FACEBOOK_SEARCH_TIMEOUT_SECONDS` keeping the shared default while `APIFY_FACEBOOK_PROFILE_TIMEOUT_SECONDS` doesn't).
- `backend/scraper/apify_twitter.py` - Apify tweet-search tier for `keyword` and `hashtag` sources, called from `source_rss.py`'s `start()` alongside their existing tiers (not in place of them, unlike the `linkedin` tier above). Gated on the same `APIFY_API_TOKEN`/`config.apify_configured()` as the LinkedIn tier (`APIFY_TWITTER_SEARCH_ACTOR`/`APIFY_TWITTER_MAX_TWEETS` are its own settings); unconfigured, it is silently skipped - a keyword/hashtag source's other tiers already report their own diagnostics, so there's nothing to fail visibly. One function, `apify_twitter_search_posts(query, ...)`, covers both source types - `start()` passes the bare keyword for `keyword` sources and `f"#{tag}"` for `hashtag` sources. Unlike the hashtag CSE tier, the actor's dataset already carries full tweet text (`url`/`fullText`/`author.userName`/`createdAt`), so `_article_from_post`-equivalent normalization happens here directly and results are yielded as articles straight away - no fxtwitter hydration hop through `_yield_article`/`_hydrate_tweet` (left untouched by this tier).
- `backend/scraper/apify_reddit.py` - Apify Reddit-scraper tier for `reddit` sources, called from `source_rss.py`'s `start()` in place of the direct reddit.com/oauth.reddit.com `.json` request once `APIFY_API_TOKEN`/`config.apify_configured()` is set (same replaces-the-seed-request treatment as `linkedin` above, not the run-alongside treatment `keyword`/`hashtag` give their own Apify tier) - Reddit blocks that endpoint outright for most requesters regardless of proxy (confirmed live: 403 on every direct request observed), so once Apify is configured, running it too adds nothing but a guaranteed-blocked entry in `source_diagnostics.json`/the dashboard's "needing attention" list. Unconfigured, `reddit` sources fall through to the plain fetch unchanged - `REDDIT_PROXY_URL`/`SCRAPE_PROXY_URL` can still make that fetch succeed on its own, and `REDDIT_OAUTH_CLIENT_ID`/`REDDIT_OAUTH_CLIENT_SECRET` are the officially-sanctioned alternative. A `reddit` source's stored URL is already a canonical subreddit/user/search reddit.com URL (`sources_store._derive_reddit_url`), and the actor accepts any of those shapes directly as a start URL, so one function, `apify_reddit_posts(reddit_url, ...)`, covers all three kinds - unlike `apify_linkedin.py`'s split between a page-posts actor and a separate search actor. The default actor's (`trudax/reddit-scraper-lite`) dataset already carries full post/comment text (`url`/`body`/`title`/`username`/`communityName`/`createdAt`), so results are yielded as articles straight away, same as the other Apify tiers.
- `backend/app/core/settings.py`'s `_infer_source_type`/`_resolve_source_type` - there is no generic "social" source_type: an x.com/twitter.com URL infers straight to whichever of `tweet` (a `/status/<id>` link), `hashtag` (`/hashtag/<tag>`), or `username` (any other path) it actually is, threads.com/threads.net infers to `linkedin`'s sibling `threads`, facebook.com/fb.com infers to `facebook`, and every other social platform this app has no dedicated scraping tier for (Instagram, TikTok, YouTube, ...) falls through to plain `web`. `_resolve_source_type` runs on every create/update and every read (`sources_store._upsert_payload`/`_normalize_record`/`_normalize_source_record`), and reassigns *any* entered source to its URL's real platform type when they disagree - e.g. picking "Reddit" but pasting a tweet URL still ends up stored as `tweet`, not an uncrawlable `reddit` source. The only types never reassigned are `hashtag`/`keyword`/`username` themselves, since their stored URL is derived FROM the chosen type (`sources_store._derive_term_url`) and is therefore always self-consistent. Because this resolution happens on every read, a legacy row still stored as `social` from before this type was removed is transparently reclassified without a migration. `tweet` (a single tracked post, added via `sources_store._derive_tweet_url`, which validates/canonicalizes an x.com/twitter.com status URL) bypasses the normal per-source Scrapy request entirely in `start()`, the same way `linkedin`/`threads`/`facebook` do - it hydrates the one already-known post directly via `_hydrate_tweet`. `web` sources also now bypass robots.txt (`start()`'s `dont_obey_robotstxt`) - since a former-`social` platform is now just a `web` source and most of those platforms disallow bots in their own robots.txt, honoring it there would mean never even attempting the fetch.
- `backend/services/articles/collect.py` - the four checks one article has to pass, and the per-source counters the dashboard reports them by: **validation** (long enough, has a title, isn't a consent/search/error page - `clean_articles`, with `content_guard.py` doing the URL/title test - the 200-character length floor is waived for a tweet (`is_tweet_url`) or a LinkedIn/Threads/Facebook post (`is_short_form_social_url`), all of which are naturally caption-length rather than article-length; confirmed live, real Facebook profile posts as short as a single hashtag were being discarded as stubs before `is_short_form_social_url` existed), **duplicate** (same URL already seen this run; near-identical bodies are additionally grouped into a `story_group` at save time, see `dedup.py`), **date window** (`_article_matches_project_window`), **already scraped** (`store.get_existing_urls`, gated on `SKIP_EXISTING_URLS`). Its own `main()` is a batch CLI entry point (reads a raw-scrape JSON file, runs the whole batch through those checks) for the manual/offline workflow below; `backend/scraper/pipelines.py`'s `StreamingCollectPipeline` reuses these same functions per-article from inside the live crawl instead - see below.
- `backend/scraper/pipelines.py` - Scrapy item pipeline that validates and saves each article the moment it's scraped (calling into `collect.py`'s functions), rather than waiting for the whole crawl to finish. Self-disables (`NotConfigured`) unless `PIPELINE_RUN_ID` is set, so a bare manual `scrapy crawl` is unaffected. This is why the dashboard's per-source breakdown for a run fills in source by source instead of only appearing once the slowest source finishes. Synchronous, unlike strata-media's equivalent: with no LLM/embedding call there is no multi-second blocking work left to overlap, only short local-Postgres round trips, so it processes items on the reactor thread rather than paying for a worker pool and the lock/counter bookkeeping that comes with one.
- `backend/services/articles/store.py` - upserts articles into Postgres, assigns each one its `story_group` (`dedup.py`), and links it to every project that owns the source it came from (`list_project_ids_for_source_url`), so one source shared by several projects feeds all of them from a single scrape. `_article_write_fields(article)` leaves out columns the article carries no value for, so the table's own DEFAULT applies rather than an explicit NULL - several analysis columns are `not null default <neutral>`, and naming one with NULL fails the constraint instead of defaulting (this cost every article in a run until a real crawl caught it).
- `backend/services/pipeline/pipeline.py` - `run_scraper_pipeline()`: runs the single `scrapy crawl source_rss` subprocess described above end to end (scrape+validate+save all interleaved), then folds the spider's end-of-run fetch diagnostics (blocked/404/DNS-failed - only knowable once the whole crawl closes) into the per-source rows the streaming pipeline already wrote live.
- `backend/main.py` - FastAPI app: scraping, sources, projects, articles (list/stats/export/import) endpoints.
- `backend/services/projects/projects_ai.py` / `backend/services/projects/project_discovery.py` - call the configured LLM via `llm_client.chat_completion` for hashtag/keyword/username/source discovery.
- `backend/app/core/` - cross-cutting infrastructure imported by every other layer, imports no feature code itself: `settings.py` (was `config.py` - single source of truth for source list and credentials; loads `backend/.env` manually, not python-dotenv; also resolves the active LLM provider (`LLM_PROVIDER`) and its credentials/base URL/model), `db.py` (the `psycopg_pool.ConnectionPool`-backed `fetch_all`/`fetch_one`/`execute`/`transaction` helpers), `logging.py` (root `dictConfig`, called once at the top of `main.py`), and `jobs.py` (the in-process `JobRegistry` for one-shot background jobs like competitor discovery/analysis and article import - see its docstring for why this is deliberately not Postgres-backed, and single-process only). Everywhere else imports these as `from app.core import settings as config` / `from app.core import db`.
- `backend/llm_client.py` - provider-neutral `chat_completion(...)` client; the only module aware of OpenAI vs. DeepSeek request/response differences.
- `backend/services/` - business-logic modules grouped by domain: `auth/` (login, sessions, users, RBAC), `projects/`, `sources/`, `competitors/` (competitor study), `articles/` (collect/store/export/import), `pipeline/` (scrape→save execution, run tracking, scheduling). `migrate.py` stays at `backend/` root.
- `dashboard/` - React 19 + Vite dashboard, calls the backend API. `/dashboard` (`DashboardPage.jsx`) is a per-project collection-health overview, backed by a single `GET /api/dashboard/summary?project_id=` (`backend/api/routers/dashboard.py` / `services/dashboard/dashboard_store.py`): totals (articles, sources, and - competitor mode only - tracked competitors), an articles-per-pipeline-run line chart, an articles-by-source breakdown, and a "needing attention" list built from the latest run's `pipeline_run_sources.fetch_note` (blocked/errored/0-articles) - sources for a sentiment project, competitors (via their linked, valid `competitor_accounts`) for a competitor-mode one. There is no cross-run persistence of source health; "needing attention" is recomputed from the single most recent run with per-source detail each time the endpoint is called.

Tests live in `backend/tests/` (unittest, run with pytest). There is no dashboard test suite.

## Handoff: export → import

The JSONL export is the only way articles leave this app, so it has to round-trip losslessly into a database that *will* analyze them:

- `articles_store._export_select()` selects exactly the columns `store.save_articles()` writes (`stored_article_fields()`), minus `EXPORT_LOCAL_ONLY_FIELDS`, built from the live table rather than hardcoded. The narrow `ARTICLES_SELECT` the dashboard uses is not enough - the upsert behind the import sets every mutable column from `excluded`, so a column the export omits comes back NULL.
- **`ARTICLE_MUTABLE_FIELDS` and the `articles` schema must stay identical to strata-media's.** A column dropped here silently becomes NULL there. This is why the analysis columns are still in the schema even though nothing populates them.
- **Database-local identifiers must not be exported.** `pipeline_run_id` is a foreign key into *this* database's `pipeline_runs`; exported, every row fails `articles_pipeline_run_id_fkey` on the importing side and nothing lands (`EXPORT_LOCAL_ONLY_FIELDS`). `story_id` is excluded for the same reason - it names a local `story_groups` row, and the importing side regroups by body similarity itself. `source_run_snapshot` (`{id, started_at, project_id}`) is `pipeline_run_id`'s exportable twin - a denormalized copy of the same run identity, captured once at save time in `services/articles/store.py`, so it is *not* in `EXPORT_LOCAL_ONLY_FIELDS` and does reach the importing side.
- **Every article is stamped `analysis_status='pending'`** (`collect.mark_unanalyzed`, with a matching fallback in `store._article_row`). The column defaults to `'success'` - it was added to a database whose rows had all been analyzed - and strata-media's analyze endpoints skip anything already marked successful, so inheriting that default would mean a whole collection run silently never gets analyzed.
- `POST /api/articles/import` (`services/articles/import_jobs.py`) filters incoming keys against `ARTICLE_MUTABLE_FIELDS` and calls the same `save_articles()` the pipeline uses - no analysis required on either side. It fails the run when rows parsed but none saved: `save_articles()` logs and swallows a rejected batch, so without that check a wholly-rejected file finishes as "success - imported 0".

## Commands

Backend (from `backend/`):
```
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
uvicorn main:app --port 8000
python -m pytest tests/ -q
```
Run pipeline manually (offline/dev, no `PIPELINE_RUN_ID` - the streaming item pipeline stays disabled): `scrapy crawl source_rss -O articles.json` then `python -m services.articles.collect`. The backend-triggered pipeline (`/scrape` endpoint, scheduler) instead runs a single `scrapy crawl source_rss` with `PIPELINE_RUN_ID` set, streaming validate+save per article - see `backend/scraper/pipelines.py`.

Dashboard (from `dashboard/`):
```
npm install
npm run dev       # dev server, expects backend at http://localhost:8000 (override via VITE_API_TARGET)
npm run build
npm run lint      # eslint .
```

Docker (full stack from repo root): `docker compose up --build`
- Public app on `:8211` (nginx), backend proxied at `/api` and `/scrape`, Adminer on `:8083`, Postgres in `db` service. Ports deliberately differ from strata-media's so both stacks can run at once.
- Backend container reads `backend/.env`.

## Constraints

- Required backend env vars: `DATABASE_URL`, plus the active LLM provider's key (`DEEPSEEK_API_KEY` by default; `OPENAI_API_KEY` if `LLM_PROVIDER=openai`; not needed for `LLM_PROVIDER=ollama`). The LLM is used only for discovery: project metadata suggestions, project keyword/hashtag/username/source discovery, and competitor discovery.
- **Separate database from strata-media.** The two apps exchange data through the JSONL export/import, never a shared table - `docker-compose.yml` uses its own `scraper` database and its own compose-project volume.
- `LLM_PROVIDER` (`deepseek` default, or `openai`, or `ollama` for a fully local/offline setup) picks the app-wide provider; all provider selection, credentials, and request-shape differences are centralized in `backend/app/core/settings.py` and `backend/llm_client.py`. Feature modules only call `llm_client.chat_completion(...)` and never branch on the provider. `ollama` talks to a local `ollama serve` (default `http://localhost:11434/v1/chat/completions`), which speaks the same OpenAI-compatible chat-completions shape as DeepSeek.
- OpenAI is called via its Responses API (`OPENAI_CHAT_MODEL`/`OPENAI_CHAT_BASE_URL` overridable; default model `gpt-5-nano`); DeepSeek via its OpenAI-compatible chat-completions API (`DEEPSEEK_CHAT_MODEL`/`DEEPSEEK_CHAT_BASE_URL` overridable; default model `deepseek-chat`).
- Keep `VITE_API_TARGET` (dashboard) consistent with the backend's actual base URL if deployed separately.
- `GOOGLE_CSE_API_KEY`/`GOOGLE_CSE_ENGINE_ID` (both optional, unset by default) enable the general-web-search tier for `keyword` sources - see `backend/scraper/web_search.py`. Unset, keyword sources are scraped via Google News RSS + GDELT (+ Apify, if configured) only. The same two vars also enable one of `hashtag` sources' two tweet-discovery tiers (tweet-link discovery via CSE, see `source_rss.py`'s `start()`) - unset, a `hashtag` source falls back to the Apify tier alone (or finds no tweets at all if that's unset too).
- `GDELT_ENABLED` (`true` by default, no credentials needed) - GDELT's free DOC 2.0 news-search API tier for `keyword` sources, see `backend/scraper/gdelt.py`. GDELT itself rate-limits to roughly one request per 5 seconds (undocumented exactly, observed stricter in practice); `gdelt.py` throttles its own calls to stay under that, so a project with many keywords takes correspondingly longer to seed this tier. Set `false` to disable.
- `APIFY_API_TOKEN` (optional, unset by default) - enables `linkedin`, `threads`, and `facebook` sources' only tier (`backend/scraper/apify_linkedin.py`/`backend/scraper/apify_threads.py`/`backend/scraper/apify_facebook.py`) and additional tiers for `keyword`/`hashtag` (tweet search, `backend/scraper/apify_twitter.py`) and `reddit` (`backend/scraper/apify_reddit.py`) sources. Get a token at https://console.apify.com/settings/integrations. Unset, a `linkedin`/`threads`/`facebook` source cannot find any posts at all (reports 0 articles with an explanatory fetch note, same as an unconfigured `hashtag` source); a `keyword`/`hashtag`/`reddit` source just loses this one tier silently, since all three already have other tiers. `APIFY_LINKEDIN_POSTS_ACTOR`/`APIFY_LINKEDIN_SEARCH_ACTOR` (both default to a `harvestapi` actor) and `APIFY_LINKEDIN_MAX_POSTS` are further overridable, as are `APIFY_THREADS_ACTOR` (defaults to `automation-lab/threads-scraper`)/`APIFY_THREADS_MAX_POSTS`, `APIFY_FACEBOOK_PAGES_ACTOR`/`APIFY_FACEBOOK_GROUPS_ACTOR`/`APIFY_FACEBOOK_SEARCH_ACTOR`/`APIFY_FACEBOOK_PROFILE_ACTOR` (default to `apify/facebook-posts-scraper`/`apify/facebook-groups-scraper`/`cleansyntax/facebook-profile-posts-scraper`/`cleansyntax/facebook-profile-posts-scraper` - all confirmed live, see `apify_facebook.py`'s module docstring; search and profile share an actor but call different endpoints on it)/`APIFY_FACEBOOK_MAX_POSTS`/`APIFY_FACEBOOK_PROFILE_MAX_POSTS` (the profile-posts endpoint's own, smaller cap - it's far slower per post than the other three), `APIFY_TWITTER_SEARCH_ACTOR` (defaults to `apidojo/tweet-scraper`)/`APIFY_TWITTER_MAX_TWEETS`, and `APIFY_REDDIT_SEARCH_ACTOR` (defaults to `trudax/reddit-scraper-lite`)/`APIFY_REDDIT_MAX_ITEMS`. Every actor gets its own timeout var too (`APIFY_LINKEDIN_POSTS_TIMEOUT_SECONDS`/`APIFY_LINKEDIN_SEARCH_TIMEOUT_SECONDS`/`APIFY_THREADS_TIMEOUT_SECONDS`/`APIFY_FACEBOOK_PAGES_TIMEOUT_SECONDS`/`APIFY_FACEBOOK_GROUPS_TIMEOUT_SECONDS`/`APIFY_FACEBOOK_SEARCH_TIMEOUT_SECONDS`/`APIFY_FACEBOOK_PROFILE_TIMEOUT_SECONDS`/`APIFY_TWITTER_SEARCH_TIMEOUT_SECONDS`/`APIFY_REDDIT_SEARCH_TIMEOUT_SECONDS`, each falling back to `APIFY_TIMEOUT_SECONDS` when unset - see `scraper/apify_common.py`'s `run_actor_sync`) rather than sharing one budget: a live subreddit was observed taking 180s+ against the shared 120s default, so `APIFY_REDDIT_SEARCH_TIMEOUT_SECONDS` alone defaults higher (240s) without stretching the others - and the Facebook profile actor was observed taking ~55s for 5 posts and still running past 270s for 20, so `APIFY_FACEBOOK_PROFILE_TIMEOUT_SECONDS` alone defaults higher too (180s), on top of its own smaller `APIFY_FACEBOOK_PROFILE_MAX_POSTS` (5, vs. the other three actors' shared `APIFY_FACEBOOK_MAX_POSTS`).
- `SKIP_EXISTING_URLS` (`true` by default) - skip re-saving a URL already in `articles`, counted per source as "already scraped". Set `false` to re-save everything each run (refreshes `fetched_at`, re-runs story-group assignment).
- A competitor study's confirmed channels only become scrapable once `competitors_store.sync_project_sources()` links them into `sources`. This is fully implicit now, from two places: `run_scraper_pipeline()` (`backend/services/pipeline/pipeline.py`) calls it for any competitor-mode project right before every run (manual "run now" or scheduled), and `competitor_api.py`'s `set_status()` calls it whenever a competitor is tracked/untracked. There is no manual "sync" action anywhere - a channel confirmed just before a run is never missed, and no UI step can be forgotten.
- `backend/schema.sql` is the migration runner's `0001_baseline` (see `migrate.py`) and currently holds the **whole** schema - migrations `0002`-`0028` were squashed back into it. The baseline is deliberately exempt from the runner's drift check: it is idempotent, and when its checksum moves the runner re-applies it, which is how an existing database picks up additive changes. Editing an applied file under `backend/migrations/` *is* a hard error - add a new `NNNN_name.sql` (starting at `0002`) instead. Because the baseline is built from `create table if not exists`, it cannot drop, retighten, or un-policy anything on a database that already has the table; anything of that kind has to be a real numbered migration. See `backend/migrations/README.md`.
